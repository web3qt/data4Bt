```go
// 设置信号处理
sigChan := make(chan os.Signal, 1)
signal.Notify(sigChan, syscall.SIGINT, syscall.SIGTERM)

// 用于跟踪是否已经开始关闭
var shutdownOnce sync.Once

go func() {
    sig := <-sigChan
    shutdownOnce.Do(func() {
        log.Info().Str("signal", sig.String()).Msg("Received shutdown signal")
        cancel() // 取消context
        
        // 设置优雅关闭超时
        go func() {
            time.Sleep(10 * time.Second)
            os.Exit(1)
        }()
    })
    
    // 第二次信号强制退出
    sig2 := <-sigChan
    os.Exit(1)
}()
```

### 2.2 go run进程模型分析

**关键发现**:
- ⚠️ **进程层级问题**: `go run`会创建两层进程结构
  - 父进程: `go run cmd/main.go` (PID: 33563)
  - 子进程: 实际的Go程序 (PID: 33585)
- ⚠️ **信号传递机制**: 直接的Ctrl+C信号可能只传递给go run父进程
- ✅ **PPID分析**: 子进程的PPID正确指向go run进程

**测试验证**:
```bash
# 测试程序输出
PID: 33585   # 实际Go程序
PPID: 33563  # go run进程

# 直接向子进程发送信号
kill -INT 33585  # ✅ 能够正确处理
```

**根本原因**:
1. **信号传递链断裂**: Ctrl+C → Shell → go run进程，但可能没有正确传递给子进程
2. **进程模型复杂性**: go run创建的临时进程结构影响信号传递

## 3. 根本原因分析

### 3.1 主要问题: go run信号传递失效

**问题描述**: 使用`go run cmd/main.go`直接运行时，Ctrl+C信号可能无法正确传递到实际的Go程序

**技术原因**:
1. **进程层级复杂**: go run创建父子进程结构
2. **信号传递机制**: Shell的Ctrl+C信号可能只传递给go run进程
3. **进程组管理**: go run可能没有正确设置进程组信号传递

**影响范围**:
- 直接使用`go run cmd/main.go`时无法通过Ctrl+C停止
- 开发调试时用户体验差
- 可能产生僵尸进程

### 3.2 次要问题: start.sh时序竞争

**问题描述**: start.sh的trap设置和go run启动之间可能存在微小的时序窗口

**技术原因**:
1. **异步启动**: go run在后台启动，trap设置可能有延迟
2. **信号竞争**: 在trap完全设置前收到信号可能处理不当

**影响范围**:
- 极少数情况下可能出现信号处理失效
- 主要在快速启动停止的场景中出现

### 3.3 设计问题: 依赖go run的进程模型

**问题描述**: 当前设计过度依赖go run的进程管理机制

**技术原因**:
1. **开发便利性**: go run便于开发，但进程模型复杂
2. **生产环境差异**: 生产环境通常使用编译后的二进制文件
3. **信号处理不一致**: go run和直接运行二进制文件的信号处理行为不同
